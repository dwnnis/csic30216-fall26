The Function

This is a different function from the one in the lecture demonstrations.

def process_records(records, threshold):
    result = []
    seen = {}
    for r in records:
        key = r.get('id')
        val = r.get('score', 0)
        if key in seen:
            continue
        seen[key] = True
        if val >= threshold:
            result.append({'id': key, 'score': val, 'status': 'pass'})
        else:
            result.append({'id': key, 'score': val, 'status': 'fail'})
    return result

Read this carefully before writing anything. Understand what it does, what each parameter means, what it returns, and what might surprise a new engineer reading this for the first time.

Your Task and What You Produce

Task: get the model to write a docstring for process_records that meets your own specification. You write the prompts, the model writes the docstring, and your job is to judge it.

You produce:

  • Your specification (Step 0)
  • Four docstrings, one per technique, each with the prompt that produced it and your analysis
  • At the end, your pair's approved docstring: the one you would approve as code steward (you may edit it, and note what you changed), with a shared paragraph explaining the choice

Which docstring counts for each technique: for zero-shot and few-shot, the model's output; for chain-of-thought, the docstring after the reasoning steps; for self-correction, the revised docstring.

Step 0 — Write Your Specification (5 minutes)

Before you write any prompt, write a specification for what a good docstring for this function should contain. Use these five fields:

  • What the function does: one sentence describing the overall behaviour.
  • Parameters: for each parameter, its name, expected type, and what it represents.
  • Returns: what the function returns, including the structure of each item and what each field means.
  • Edge cases: at least two behaviours a new engineer might not anticipate from reading the code.
  • Format: which docstring style (Google, NumPy, plain prose) and any length constraint.

Keep this visible throughout the lab. Every output you evaluate gets checked against it — not against a general sense of quality.

Part 1 — Four Techniques (35 minutes)

Run each technique on the function above. For each one: the prompt verbatim, the full output, and a short analysis.

Use whichever model and interface you have access to — Claude.ai, ChatGPT, Gemini, or the API. The lab works on any interface.

Technique 1: Zero-shot

Write a prompt asking the model to write a docstring for this function. Write it naturally — no examples, no reasoning scaffold.

Record:

  • Your prompt (verbatim)
  • The full model output
  • Analysis (2–3 sentences): which fields from your specification did this satisfy? Which did it miss or handle inaccurately? Name the field and describe the gap specifically.

Technique 2: Few-shot

Three (function, docstring) example pairs are provided on the Course Website. Download them before the session. Use all three as examples before your task prompt.

Record:

  • Your full prompt including examples (verbatim — include the examples)
  • The full model output
  • Analysis (2–3 sentences): what changed compared to zero-shot? Did format improve? Did the examples help with the edge case fields from your specification? Did anything get worse?

Technique 3: Chain-of-thought

Write a prompt that asks the model to reason explicitly before writing the docstring. Use the explicit CoT structure from the lecture: instruct the model to first describe what the function does, then identify the parameters, then identify the return value, then identify at least one non-obvious edge case, and then write the docstring.

Record:

  • Your prompt (verbatim)
  • The full model output including the reasoning steps
  • Analysis (2–3 sentences): did the reasoning steps improve the docstring? Point to a specific place where the reasoning led to a better or worse result than zero-shot. Did the model identify the edge cases from your specification?

Technique 4: Self-correction

Generate an initial docstring using any prompt. Then write a critique prompt that evaluates the output against your specification using specific criteria — at least one criterion per field in your specification. Then run the revision.

Record:

  • Your generation prompt (verbatim)
  • The initial output
  • Your critique prompt (verbatim) — must contain at least three specific criteria, each checkable as pass/fail
  • The critique output
  • The revised output
  • Analysis (2–3 sentences): did the critique identify a genuine problem from your specification? Did the revision address it? Did the critique approve anything your specification would have failed?

Part 2 — Pair Discussion, Approved Docstring, and Exit Ticket (10 minutes)

Pair with the person next to you. Spend five minutes comparing your four docstrings and discussing, then five minutes picking one and writing one paragraph together.

Discussion: if you were the code steward reviewing a PR that added a docstring to this function, which of your docstrings would you approve? Which would you send back for revision, and with what comment?

Approved docstring (one per pair): pick the one docstring your pair would approve, from either partner's four. You may edit it before approving; if you do, note what you changed and why.

Shared paragraph (one per pair): 4–6 sentences explaining your choice. Which technique produced the docstring you would most trust in production, and why? Your reasoning must reference your specifications and must address cost — if this were a system generating thousands of docstrings, does your answer change?

Notes

The function is intentionally non-trivial. process_records has several behaviours worth documenting. It deduplicates by id, keeping only the first occurrence. It uses 0 as the score when the score key is missing. Each returned item is a dictionary with id, score, and status. It raises no error for records without an id — instead it treats them all as having id None, so only the first such record is kept and the rest are silently dropped as duplicates. A good docstring addresses at least two of these.

If you finish early: try step-back prompting — ask the model “what makes a good docstring for a function that filters and transforms records?” first, then use that answer as context before asking for the specific docstring. Step-back appears in Assignment 1 Part 1. This is optional and not required for the submission.

Connection to Assignment 1: Assignment 1 Part 1 uses the same structure — five techniques on a code generation task (you add step-back), prompt verbatim, full output, analysis. Students who write specific, specification-driven analyses here write better Assignment 1 submissions. The habit of checking against a written specification rather than a general sense of quality is exactly what the assignment grades.
