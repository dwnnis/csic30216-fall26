Week 11 Self-Paced Module: What a Benchmark Can Tell You, and What Only You Can Write Down

{{ site.course_code }} · {{ site.course_semester }}

Overview

The lecture asked how you know AI-written code is right. This module asks the same question one level up, about AI coding benchmarks: what does a model's score on HumanEval or SWE-bench tell you, and what does it leave out? It then turns to the one kind of evidence no benchmark and no test can produce: a written record of why the code is the way it is. That record is part of your CP2 evidence (PR descriptions and DECISIONS.md).

Why This Matters

A benchmark is a test suite written by someone else, about tasks that are not yours — the Week 10 lesson at a larger scale. HumanEval's scores cluster near the top today partly because its tests were too thin: adding far more tests dropped scores and changed rankings. SWE-bench Verified went further: an audit of the problems top models still failed found that most of them had flawed tests, not flawed models, which is why OpenAI stopped reporting it in February 2026. None of today's benchmarks check whether code is secure, fast enough, maintainable, or a fit for your codebase — a model can score well on "correct" while being exploitable on half its correct answers. And even a perfect test suite only shows what your code does, never why it does it that way: the alternatives considered, the one that was rejected, the person who decided. With AI that gap widens, because the options you never picked disappear with the chat window. A short decision record is the only thing that closes it.

What You'll Learn

  • HumanEval: the first standard benchmark — 164 hand-written Python problems, each a function signature and docstring, judged by hidden unit tests rather than by how much the code resembles a reference answer. pass@k is the chance that at least one of k samples passes all the tests.
  • Why HumanEval stopped telling models apart — frontier models now solve nearly all of its short, self-contained problems, so scores cluster near the top. Adding about 80 times more tests per problem (EvalPlus) dropped scores by up to 19–29% and changed rankings: code that “passed” was sometimes wrong. A score near 100% can mean the benchmark ran out of questions to ask, not that the model ran out of mistakes.
  • SWE-bench: real issues from real repositories — the model gets a full codebase and a GitHub issue, and must produce a patch that fixes the issue's tests without breaking the existing ones (a median of 51 per task). Far closer to project work than a self-contained function.
  • Why OpenAI stopped reporting SWE-bench Verified — an audit of 138 unsolved problems found material test issues (too narrow or too wide) in 59.4% of them, plus signs that models could reproduce the original fixes. Near the top of a benchmark, the remaining “failures” can be failures of the test, not the model — the same thing to check when your own ten-case suite keeps failing one test.
  • What coding benchmarks don't measure — security (BaxBench found about half of functionally correct backend programs were exploitable), performance at real scale, maintainability, and fit with your team's codebase and conventions. A high score is evidence a model can produce test-passing patches for well-described issues in popular open-source projects — not that it will do so safely and maintainably in yours.
  • “What” versus “why” — code shows what happens and tests show what is required, but neither shows why a particular approach was chosen over the alternatives that were considered and rejected. If that reasoning isn't written down, it exists only in a chat window and in one person's memory.
  • Why AI widens the documentation gap — generation is cheap, so the options you never picked disappear; the conversation that produced the final answer lives in a chat nobody else reads; and there may be no single person who can say why the code is the way it is. Without that record, teammates can only blindly accept a decision or blindly change it.
  • Two short records that close the gap — a decision record in DECISIONS.md (Context, Decision, Status, Consequences), and a short PR description for AI-assisted code: what you asked for, what you changed and why, alternatives considered and rejected, and how you checked it.

Optional Materials

If you want to go deeper on any of these topics (not required, but helpful if you're curious):

  • Jimenez et al. (2023), “SWE-bench: Can Language Models Resolve Real-World GitHub Issues?” — the original SWE-bench paper. Read the introduction and the section on how tasks are collected and evaluated.
  • Liu et al. (2023), “Is Your Code Generated by ChatGPT Really Correct? (EvalPlus)” — how adding many more tests to HumanEval changed scores and rankings.
  • Deng et al. (Scale AI, 2025), “SWE-Bench Pro” — the harder successor to SWE-bench: larger changes, held-out and commercial tasks.
  • Vero et al. (2025), “BaxBench: Can LLMs Generate Correct and Secure Backends?” — correct is not the same as secure.
